# 数据存储与持久化 —— 「任何设备打开，数据都在」

> 一句话：**数据在服务器上，不在你的设备上。**

---

## 一、数据存在哪

### 架构

```
   你的手机 ─────┐
   朋友的手机 ───┼──→  云服务器（新加坡）
   你的电脑 ─────┘      ├─ /opt/chat-room/data/chat.db     ← 所有消息
                       ├─ /opt/chat-room/data/room.key     ← 房间口令
                       └─ /opt/chat-room/data/chat.db-wal  ← 写入日志（SQLite 自动）
```

### 三种存储的分工

| 存在哪 | 存什么 | 换设备会丢吗 |
|---|---|---|
| **服务器 SQLite**（`chat.db`） | 所有聊天消息、历史昵称占用记录 | ❌ **不会丢** |
| **服务器文件**（`room.key`） | 12 位房间口令 | ❌ 不会丢 |
| **浏览器 localStorage** | 只有「我是谁」的匿名设备 ID | ✅ 会丢（无所谓） |

### 关键点

**消息从来没存在浏览器里。**

打开页面时，客户端向服务端要一次历史：

```javascript
state.messages = data.history.slice();   // public/app.js
```

服务端返回 `init` 消息，里面带着最近一页历史。**关掉浏览器、换台手机、清缓存、重装系统**——再打开，同一个地址，看到的还是同一份消息。

浏览器本地只存了一个随机生成的设备 ID（`cid`），用途是让服务端知道「这个连接还是刚才那个人」。删了也不影响：新开一个连接，服务端会分配一个新昵称，**消息记录一条不少**。

## 二、数据库结构

两个表，都在 `data/chat.db`：

### `users` —— 昵称占用权

```sql
CREATE TABLE users (
  id         TEXT PRIMARY KEY,
  name       TEXT NOT NULL UNIQUE,   -- ← 唯一索引，昵称不能重复
  color      TEXT,
  last_seen  INTEGER                  -- 最后在线时间
);
```

**这个表就是「历史昵称去重」的实现方式。**

- 用户离线后，`users` 行**不会被立即删除**
- 所以「云朵」这个昵称用过了，以后谁都不能再用
- 唯一索引 `idx_users_name` 在数据库层面兜底，防止并发时两个连接抢同一个昵称

**昵称什么时候能被释放？**

看代码里的清理规则：

```sql
DELETE FROM users
WHERE id NOT IN (SELECT DISTINCT sender_id FROM messages)   -- 没发过任何消息
  AND last_seen < ?                                        -- 且超过保留期
```

即：

| 情况 | 昵称占用 |
|---|---|
| 发过消息的人，离线中 | **一直占用**（直到消息本身过期） |
| 只进过聊天室没说话，超过 7 天 | 释放，可用 |
| 消息被清理（超过 7 天） | 对应昵称**同时**释放 |

> **设计上昵称占用期和消息保留期是对齐的（都是 7 天）。**
> 你朋友用了「小明」，下线三天后你想用「小明」—— 用不了。
> 这是你之前明确要求的行为，代码里已实现并有测试覆盖。

### `messages` —— 聊天内容

```sql
CREATE TABLE messages (
  id           TEXT PRIMARY KEY,
  sender_id    TEXT,
  text         TEXT,
  kind         TEXT,        -- text / system 等
  reply_to_id  TEXT,        -- 引用消息
  created_at   INTEGER      -- 毫秒时间戳
);
```

### 消息保留策略

- **保留 7 天**，超期自动清理
- **撤回时限 2 分钟**
- 撤回是软删除（消息体被替换），不是物理删除
- 昵称占用期与消息保留期**对齐**（都是 7 天，见上文）

## 三、验证「数据真的在服务端」

### 方法 1：换浏览器查历史

1. 在电脑 A 上打开聊天室，发几条消息
2. 换手机 / 换浏览器 / 无痕窗口打开同一个链接
3. **历史消息都在** → 证明存在服务端

### 方法 2：直接查数据库（服务器上）

```bash
cd /opt/chat-room
node -e "
const {DatabaseSync}=require('node:sqlite');
const db=new DatabaseSync('data/chat.db');
console.log('消息数:', db.prepare('select count(*) c from messages').get().c);
console.log('占用昵称:', db.prepare('select name from users').all().map(u=>u.name).join(', '));
"
```

### 方法 3：看文件时间戳

```bash
ls -la /opt/chat-room/data/
# chat.db 的大小和修改时间 = 服务端确实在写
```

## 四、备份与迁移

### 备份

```bash
cd /opt/chat-room
bash deploy/backup.sh
```

生成 `backups/chat-data-<时间戳>.tar.gz`，里面是：

- `chat.db` —— 所有消息 + 昵称占用
- `room.key` —— 房间口令

> 备份用的是 SQLite 的 `.backup` 命令做**一致性快照**，
> 即使服务正在写入也不会拿到损坏的库。

### 迁移到新服务器

```bash
# 1. 旧服务器上备份
bash deploy/backup.sh
# → /opt/chat-room/backups/chat-data-20261125-111259.tar.gz

# 2. 把这个包传到新服务器
scp /opt/chat-room/backups/chat-data-*.tar.gz root@新IP:/root/

# 3. 新服务器上部署完，再还原
systemctl stop chat-room
tar -xzf /root/chat-data-*.tar.gz -C /opt/chat-room/data
systemctl start chat-room
```

**口令一致 → 朋友原来那条链接直接还能用**，不用重新发。

### 你的情况（1 个月轻量到期）

服务器 2026-12-26 到期。到期前记得：

```bash
bash deploy/backup.sh
```

把 tar.gz 存到本地或网盘。换服务器后按上面第 3 步还原即可。

## 五、几种情况下的数据归属

| 场景 | 数据在哪 | 怎么办 |
|---|---|---|
| 本机跑隧道（本机是"服务器"） | 你电脑的 `data/` 目录 | 电脑关机数据就不可访问，但**文件还在**，重开还在 |
| 部署到云服务器 | 服务器的 `/opt/chat-room/data/` | 换设备访问同一地址，数据都在 |
| 服务器到期 | 还在服务器上（但服务停了） | 先 `backup.sh` 再迁移 |
| 删了 `data/chat.db` | **数据真没了** | 只能靠备份恢复 |
| 清浏览器缓存 | **不影响** | 浏览器本地只有设备 ID |

## 六、注意事项

### 别删 `data/` 目录

```bash
rm -rf /opt/chat-room/data   # ❌ 绝对不要
```

删了 = 所有消息和历史昵称永久丢失。

### 改房间口令

口令存在 `data/room.key`，改它就等于换锁：

```bash
echo -n "新口令" > /opt/chat-room/data/room.key
systemctl restart chat-room
```

> 注意：新口令要自己写进文件（服务端只在**文件不存在**时才自动生成）。
> 改完记得重新把带新口令的链接发给朋友。

### 数据量

聊天记录很小 —— SQLite 单文件，几百 MB 能存几十万条消息。
你这种两人内测，几年都撑不满一个备份包。

## 七、和「昵称去重」的关系

两个机制配合：

1. **`users` 表 + 唯一索引** → 保证昵称不重复（哪怕人已经离线）
2. **`last_seen` + 定期清理** → 长时间不活跃的昵称才被释放

效果：**你朋友用了「小明」，下线三天后你想用「小明」—— 用不了**，因为他的记录还在。
这是你之前明确要求的行为，代码里已经实现并有测试覆盖：
