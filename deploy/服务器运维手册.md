## 二、架构

```
                    公网
                     │
      ┌──────────────┴──────────────┐
      │                             │
  :80 (Nginx)                  :443 (Nginx, TLS)
      │                             │
      │  ACME http-01 验证            │  wss:// 加密聊天
      │  (证书续期用)                  │
      └─────────────┬───────────────┘
                    │  proxy_pass
                    ▼
            127.0.0.1:8000
              (Node 服务)
                    │
                    ▼
            SQLite: data/chat.db
```

**关键点**：Node 只监听 `127.0.0.1:8000`，**公网打不通 8000**。
所有外部流量必须经过 Nginx，这样才有 HTTPS 小锁和 wss 加密。

## 三、端口现状

| 端口 | 状态 | 用途 |
|---|---|---|
| 22 | 云防火墙放行 | SSH（公钥认证） |
| 80 | 云防火墙放行 | ACME 证书验证 + HTTP 301 跳 HTTPS |
| 443 | 云防火墙放行 | HTTPS 入口 |
| 8000 | **公网不可达**（云防火墙规则待删除） | Node 只监听本机回环 `127.0.0.1:8000` |

> 8000 的云防火墙规则需要用户在阿里云 App 里手动删除（轻量应用服务器的
> 防火墙规则不支持 API/元数据操作，必须在控制台点）。
> 删除后规则表里只剩 22 / 80 / 443。
> 排查时若需临时对外暴露 Node，改 `127.0.0.1:8000` 的绑定地址
> 并临时加回防火墙规则即可，**平时保持只监听回环**。

## 四、证书

| 项目 | 值 |
|---|---|
| 类型 | Let's Encrypt **IP 证书**（shortlived profile） |
| 签发对象 | `IP Address:8.222.185.143` |
| 有效期 | **7 天**（2026-11-25 → 2026-12-02） |
| 续期方式 | cron（每天 03:00）+ systemd timer（每天，随机延迟 1 小时）双保险 |
| 下次续期 | 2026-11-27 |

**为什么只有 7 天**：Let's Encrypt 对 IP 地址证书只提供 shortlived 配置。
有域名就能签 90 天的标准证书，见 [`域名绑定.md`](./域名绑定.md)。

### 手动续期

```bash
/root/.acme.sh/acme.sh --renew -d 8.222.185.143 --ecc --force
systemctl reload nginx
```

### 查看证书信息

```bash
openssl x509 -in /etc/nginx/ssl/chatroom/fullchain.pem -noout -dates -subject
/root/.acme.sh/acme.sh --info -d 8.222.185.143 --ecc
```

```

### 更新代码（GitHub 改了之后）

```bash
cd /opt/chat-room/app
git fetch --depth 1 origin main
git reset --hard FETCH_HEAD
systemctl restart chat-room
bash deploy/verify.sh --ip 8.222.185.143 --port 8000 --dir /opt/chat-room/app
```

> ⚠️ 用 `fetch + reset --hard`，**不要用 `git pull`**。
> 服务器是 `--depth 1` 浅克隆，`git pull` 会因为历史不一致报错
> `fatal: Need to specify how to reconcile divergent branches`。

### 数据备份

```

产出 `/opt/chat-room/app/backups/chat-data-<时间戳>.tar.gz`，
内含 `chat.db` + `room.key`，**口令一致 → 迁移后朋友原链接直接还能用**。

### 一键体检

```bash

bash deploy/verify.sh --ip 8.222.185.143 --port 8000 --dir /opt/chat-room/app

## 六、到期与迁移

**到期日：2026-12-26**（1 个月，¥0 优惠券买的）

阿里云轻量到期规则：
- 到期自动停机 → **数据保留 15 天**
- 15 天内续费可原样恢复
- **超 15 天实例/快照/镜像永久删除，数据不可恢复**

### 迁移步骤

```bash
# 1. 旧机器导出
cd /opt/chat-room/app && bash deploy/backup.sh
ls -t /opt/chat-room/app/backups/*.tar.gz | head -1

# 2. 下载这个包（scp 或在控制台文件管理里下载）
#    scp root@8.222.185.143:/opt/chat-room/app/backups/chat-data-XXX.tar.gz ./

# 3. 新机器部署（先跑 grant-ssh.sh 授权）
cd /opt/chat-room/app && bash deploy/deploy.sh --port 8000 --dir /opt/chat-room/app

# 4. 还原数据
tar -xzf chat-data-XXX.tar.gz -C /opt/chat-room/app/data
systemctl restart chat-room

# 5. 配 HTTPS（IP 变了的话）
bash deploy/https-setup.sh --ip <新IP> --port 8000 --dir /opt/chat-room/app
```

> 迁移后**口令不变**，但链接里的 IP 要改成新的。
> 如果新机器也用同一个 IP 方案，朋友的链接一个字都不用改。

## 七、故障排查

| 现象 | 排查 | 解决 |
|---|---|---|
| 打开是 HTTP 无小锁 | Nginx 没起或证书没装 | `nginx -t && systemctl reload nginx`；看 `/etc/nginx/ssl/chatroom/` 有没有文件 |
| `502 Bad Gateway` | Node 服务挂了 | `systemctl status chat-room`；`journalctl -u chat-room -n 50` |
| 证书过期 | shortlived 到期（7 天） | `acme.sh --renew -d 8.222.185.143 --ecc --force`；检查 cron/timer 还在不在 |
| 签证书超时 | 80 端口不通 | 云防火墙放行 80；`ufw status` 看本机有没有拦 |
| 朋友说进不去 | 口令不对 | `cat /opt/chat-room/app/data/room.key` |
| 消息发不出去 | Nginx 缺 `/ws` 反代配置 | `grep -A5 "location /ws" /etc/nginx/sites-available/chat-room` |
| 成员列表有人但不该有 | 旧连接没断 | 正常现象，7 天后自动清理；也可重启服务清空在线列表 |

## 八、已知的坑（下次别再踩）

1. **`get.acme.sh` 的第一个位置参数是「邮箱」**
   `sh install.sh --home /xxx` 会被当成邮箱传给 acme.sh，报
   `Unknown parameter: ----home`。正确做法：root 下直接 `sh install.sh` 不带参数。

2. **阿里云元数据不一定有 `public-ipv4`**
   本机只有 `eipv4`。请求不存在的路径会返回 **404 的 HTML 页面**，
   curl 不加校验就会把整段 XML 当成 IP。所有 IP 来源都要 `grep -qE '^[0-9]+\.[0-9]+...'`。

3. **apt 会被 unattended-upgrades 抢锁**
   `E: Could not get lock /var/lib/dpkg/lock-frontend`。
   先 `fuser /var/lib/dpkg/lock-frontend` 等它释放，或最多等 120 秒。

4. **Workbench 登录的是 `admin` 不是 `root`**
   公钥要写到 `/root/.ssh/authorized_keys` 并 `chown root:root`，
   否则助手用 root 连不上。

5. **浅克隆不能用 `git pull`**
   用 `git fetch --depth 1 origin main && git reset --hard FETCH_HEAD`。

6. **服务端是先升级握手、再发 bad_key**
   所以 WebSocket 客户端的 `open` 事件**必然先于** `bad_key` 消息到达，
   不能用 `open` 判定「连上了」，真正的判据是后续消息里有没有 `bad_key`。
