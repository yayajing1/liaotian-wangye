# 多人网页聊天室

一个部署在公网的多人聊天室。浏览器打开即用，**无需注册登录**。

核心设计:**自己发的消息在右边，别人的在左边**（参照 QQ / 微信的会话布局）。

> 📦 **在国内看这份源码打不开？** GitHub 网页偶尔会连不上或加载半天，
> 这跟仓库没关系。三种绕法任选：
> 1. 仓库主页右上角 **Code → Download ZIP**（走 github.com，一般能通）；
> 2. 换网络环境（手机流量 / 换 Wi-Fi）再打开；
> 3. 直接找发仓库的人要一份打包好的 zip。
>
> 想看代码又不方便上 GitHub，也可以先 `git clone` 到本地再看。

## 快速开始

**已经有服务器？** 照着 [`deploy/买完服务器之后.md`](deploy/买完服务器之后.md) 做，
一条命令搞定部署。核心三条：

```bash
mkdir -p /opt/chat-room && cd /opt/chat-room
git clone --depth 1 https://github.com/yayajing1/liaotian-wangye.git app && cd app
bash deploy/deploy.sh && bash deploy/https-setup.sh
```

**本地先试试？**

```bash
npm install && npm start
```

然后打开 <http://localhost:8000>。

**怎么让朋友进来？** 见[「让朋友进来」](#二让朋友进来三种方式按需选)。
核心就一句话：**必须是公网地址，`localhost` 朋友永远打不开**。

## 功能特性

| 能力 | 说明 |
|---|---|
| 实时消息 | WebSocket 长连接，3-10 人小组场景延迟 < 100ms |
| 消息布局 | 自己右对齐（蓝气泡），他人左对齐（白气泡），连续消息自动分组 |
| 视觉风格 | 聊天区**浅蓝背景**，侧栏行楷「聊天网页」标题 |
| 头像配色 | 6 色系（浅绿/浅粉/浅黄/浅紫/白/黑）× 4 色阶 = **24 色**，**同色系内亮度差 ≥ 20**，保证 20 人以内不撞色 |
| 头像文字 | 消息区显示**昵称两字缩写**（"晚风"→"晚风"，"青柠老师"→"青师"），同首字的人也能分辨 |
| 身份 | 进房自动分配昵称 + 头像色，随时可改名（12 字符内） |
| **身份持久** | 身份存在浏览器 localStorage，**刷新页面 / 关掉重开仍是同一个人**（id、昵称、颜色都不变），自己的历史消息不会被误判到左边 |
| 改名同步 | 改昵称后，该用户**此前的历史消息也一并显示新昵称** |
| 重名处理 | 昵称**全局唯一**（在线成员 + 历史消息里的老用户一起算），冲突时自动加数字后缀（如 `小满2`） |
| 撤回 | 只能撤回**自己**的消息，2 分钟内有效，撤回后显示「消息已被撤回」 |
| 引用回复 | 消息 hover 点「引用」，新消息顶部显示引用条 |
| 表情 | 内置 40 个常用 emoji，纯前端实现 |
| 在线成员 | 侧栏实时显示在线名单，自己标「我」 |
| 输入提示 | 实时显示「XX 正在输入…」 |
| 未读计数 | 窗口未聚焦时标签页标题累计 `(n)`，聚焦后清零 |
| 消息持久化 | SQLite 单文件，**保留 7 天**后自动过期清理 |
| 断线重连 | 指数退避自动重连（1s → 2s → 4s → 最长 30s），界面显示连接状态 |

**明确不做**：登录注册、移动端适配、管理功能（禁言/踢人）、图片文件上传、多房间私聊、@提醒、断线补发、发送限频。

## 一、本地启动

需要 **Node.js ≥ 22**（用到内置的 `node:sqlite`）。

```bash
npm install
npm start
```

打开 <http://localhost:8000> → 看到行楷「聊天网页」入口页，**点击页面（或等 5 秒倒计时）即进入聊天室**。
聊天室本体地址是 <http://localhost:8000/chat>。

> 服务同时监听 **8000**（主）和 **3000**（备用）两个端口，是同一套服务、同一份数据。
> 想换端口：`PORT=8080 ALT_PORT=3001 node server.js`。

> `node:sqlite` 目前会打印一条 `ExperimentalWarning`，属正常现象，不影响功能。
> 想消掉可在启动时加 `--no-warnings`：`node --no-warnings server.js`

### 试多人效果

最简单的方式是**开多个浏览器窗口**（同一个窗口的多个标签页也各自算独立用户）：

- 普通窗口 + 无痕窗口各开一个 → 2 个用户
- 局域网内其他电脑访问 `http://<你的内网IP>:8000` → 也是独立用户

### 让朋友从自己的电脑加入

服务默认监听 `0.0.0.0`，也就是**接受所有网卡的连接**，同一 WiFi 下的朋友可以直接访问：

```bash
# 查看你的局域网 IP（Windows）
ipconfig
# IPv4 地址，例如 192.168.1.23
```

把这个地址发给朋友：

```
http://192.168.1.23:8000
```

朋友打开就能进聊天室，会自动拿到自己的昵称和头像色，**和你在同一个房间里**。

**如果朋友打不开**，按顺序排查：

| 现象 | 原因 | 处理 |
|---|---|---|
| 浏览器一直转圈 | Windows 防火墙拦截 | 首次访问时 Windows 会弹「是否允许 Node.js 通信」，选**允许**；或手动放行该端口 |
| 能打开但发不出消息 | 页面被当成 `file://` 打开 | 必须用 `http://` 地址，不能双击本地 html 文件 |
| 双方不在一个房间 | 朋友连的是另一个端口 | 确认两边都是 `8000`（备用 `3000` 也能互通，服务是同一套） |

> 防火墙规则：Windows 通常会在你第一次运行 `node` 时自动为 `node.exe` 建立入站放行规则。
> 若没有，以管理员身份运行 PowerShell 执行：
> ```powershell
> New-NetFirewallRule -DisplayName "Node Chat 8000" -Direction Inbound -Protocol TCP -LocalPort 8000 -Action Allow
> ```

### 每个人看到的左右布局

**左右是相对于"看的人"而言的**：

| 谁在看 | 谁发的消息 | 显示位置 |
|---|---|---|
| 你 | 你自己发的 | **右边**（蓝气泡） |
| 你 | 朋友发的 | 左边（白气泡） |
| 朋友 | 你发的 | 左边（白气泡） |
| 朋友 | 朋友自己发的 | **右边**（蓝气泡） |

同一句话，在每个人屏幕上都会自动落到"自己右边、别人左边"。

## 二、让朋友进来（三种方式，按需选）

> ⚠️ **先说一个最容易踩的坑**：`http://localhost:8000` **只有你自己能打开**。
> `localhost` 永远指向"访问者自己的那台电脑"——你朋友在他自己电脑上敲这个地址，
> 连的是他自己的机器，**不是你这里的**。要让他进来，必须给他一个**公网可达的地址**。

| 方式 | 朋友访问的地址 | 需要什么 | 适合 |
|---|---|---|---|
| **C. 云服务器**（最正规）⭐ | `https://<服务器IP>/chat#key=xxx` | 一台云主机（域名可选） | **长期稳定使用** |
| A. 本机穿透（最快，5 分钟） | `https://xxx.trycloudflare.com` | 无，只需本机能上网 | 先试试效果、临时用 |
| B. 家庭宽带直连 | `http://<你的公网IP>:8000` | 公网 IP、路由器端口映射 | 长期用但不想买服务器 |

三种方式**用的是同一套代码**，切换方式不用改任何业务逻辑。

> 💡 **为什么不能直接传到 Vercel / EdgeOne Pages 这类静态托管平台？**
>
> 静态托管的工作方式是「上传 HTML/CSS/JS → 平台返回文件」，它的服务器**不跑你的代码**。
> 而这个聊天室需要三样静态托管给不了的东西：
>
> | 需要什么 | 静态托管 |
> |---|---|
> | `public/` 里的页面和样式 | ✅ 能托管 |
> | **WebSocket 长连接**（消息实时推送） | ❌ 只能处理一次性 HTTP 请求 |
> | **SQLite 数据库**（消息落库、历史昵称去重） | ❌ 没有服务端进程就没有数据库 |
> | **服务端生成房间口令**（挡住陌生人） | ❌ 口令逻辑在 `server.js` 里 |
>
> 所以本项目要部署到**能跑 Node.js 进程**的地方 —— 也就是云服务器。
> 好消息是改造量几乎为零：`server.js` 已经把所有关键项做成了环境变量
> （`PORT` / `HOST` / `DATA_DIR` / `ROOM_KEY`），加个 systemd 服务就行。
> 新手请直接看 **[`deploy/云服务器部署指南.md`](deploy/云服务器部署指南.md)**。

### 方式 A：本机穿透（Cloudflare Tunnel）

不需要域名、不需要备案、不需要服务器，5 分钟出结果。

**一键启动（推荐）**：在项目根目录运行

```bash
node launch.js
```

它会自动起服务、起隧道，并把公网地址打印出来，同时打开本机页面。
`Ctrl+C` 一并关掉两个进程。

**手动启动**：

```bash
# 终端 1：启动服务
npm start

# 终端 2：启动隧道
node_modules/@camera.ui/cloudflared-win32-x64/cloudflared.exe tunnel --url http://localhost:8000
```

输出里会有一行：

```
|  Your quick Tunnel has been created! Visit it at (it may take some time to be reachable):
|  https://xxxx-xxxx-xxxx.trycloudflare.com
```

**把 `https://xxxx-xxxx-xxxx.trycloudflare.com` 发给朋友即可**，他打开就能进聊天室。

> ✅ Cloudflare 隧道**自带 HTTPS**，所以 WebSocket 自动是 `wss://`，
> 不会有"页面是 https 但 WS 是 ws://"的混合内容问题，**无需任何额外配置**。

**验证**：把地址发之前，先自己开一次，确认能进；再看朋友那边能不能发消息。

**这个方式的限制**（要知道）：

- 地址**每次启动都不一样**，重启电脑或关掉隧道后要重新发新地址给朋友
- 需要这台电脑一直开着、服务一直跑着
- Cloudflare 的免费快速隧道**没有可用性保证**，只适合试用/临时
- 想固定地址 → 见下方「固定域名」

#### 固定域名（让地址永久不变）

Cloudflare 账号 + 一个自己的域名，建一条命名隧道：

```bash
cloudflared tunnel login
cloudflared tunnel create chat-room
cloudflared tunnel route dns chat-room chat.example.com
```

然后写 `~/.cloudflared/config.yml`：

```yaml
tunnel: <你的 tunnel ID>
credentials-file: C:\Users\31217\.cloudflared\<Tunnel ID>.json

ingress:
  - hostname: chat.example.com
    service: http://localhost:8000
  - service: http_status:404
```

启动：`cloudflared tunnel run chat-room`

之后 `https://chat.example.com` 就是**永久地址**，重启不变。

### 方式 B：家庭宽带直连

路由器端口映射 + 公网 IP，详见下方「方式 C」里的排查思路，区别是：

1. 路由器后台配置端口映射：外部 `8000` → 内部 `192.168.x.x:8000`
2. 确认你的公网 IP（`curl ifconfig.me`），有些宽带是动态 IP，会变
3. 云厂商的安全组不适用，但 Windows 防火墙要放行（见下）

```powershell
# 以管理员身份运行 PowerShell
New-NetFirewallRule -DisplayName "Node Chat 8000" -Direction Inbound -Protocol TCP -LocalPort 8000 -Action Allow
```

> 没有公网 IP（运营商做了 NAT）的话这条路走不通，直接用方式 A 或 C。

### 方式 C：云服务器（最正规，推荐长期使用）

需要一台公网云主机（阿里云/腾讯云/etc.）。**新手从
[`deploy/云服务器部署指南.md`](deploy/云服务器部署指南.md) 开始** —— 里面有完整的
买服务器 → 部署 → 放行端口 → 验证的全流程，
外加地域选择的决策说明（**内地服务器要备案，境外/港澳台服务器免备案**）。

#### 部署后的两种访问形态

| 形态 | 地址 | 说明 |
|---|---|---|
| **IP + HTTPS**（推荐） | `https://<服务器IP>/chat#key=xxx` | 地址栏有小锁，聊天走 `wss://` |
| IP + HTTP（最简） | `http://<服务器IP>:8000/chat#key=xxx` | 不配证书也能用，但明文传输 |

> 💡 **没有域名也能有 HTTPS**：Let's Encrypt 从 2026 年 1 月起支持给
> **IP 地址**签发证书（有效期约 6 天，需自动续期，脚本已配好 cron + systemd 双保险）。
> 详见 [`deploy/HTTPS配置.md`](deploy/HTTPS配置.md)。
>
> 有域名的话证书有效期是 **90 天**，续期频率差 30 倍，更省心。
> 详见 [`deploy/域名绑定.md`](deploy/域名绑定.md)。

最快路径是三步（**不用传任何文件，直接从 GitHub 拉代码**）：

```bash
# 1. 服务器上拉代码
mkdir -p /opt/chat-room && cd /opt/chat-room
git clone --depth 1 https://github.com/yayajing1/liaotian-wangye.git app
cd app

# 2. 一键部署（装 Node / 依赖 / 建用户 / 注册 systemd / 自检）
bash deploy/deploy.sh

# 3. 配 HTTPS（签 Let's Encrypt 证书，地址栏有小锁，聊天走 wss）
bash deploy/https-setup.sh
```

跑完终端会打印**带口令的访问链接**，直接发给朋友即可：

```
https://<服务器IP>/chat#key=xxxxxxxxxxxx
```

> 💡 **为什么不用 scp 传包？** 代码已经在 GitHub 上，服务器能直接 clone，
> 省掉「本地打包 → 上传 → 解压」三个环节，也不怕传漏文件。
>
> 如果服务器上没装 git，`deploy.sh` 会自动装。
> 如果 clone 因为网络原因失败，脚本会自动降级为下载压缩包。

脚本会自动装 Node.js（不够 22 就从 npmmirror 下）、装依赖、建 `chatroom` 用户、
注册 systemd 服务（开机自启 + 崩溃自动重启），最后打印访问地址和房间口令。

> ⚠️ **别忘了在云控制台的防火墙放行端口** —— 这是「服务器上跑得好好的但外面打不开」
> 最常见的原因。走 HTTPS 的话放行 **80**（签证书要用）和 **443**（HTTPS 入口）。

#### 部署完成后跑一次体检

```bash
cd /opt/chat-room/app
bash deploy/verify.sh
```

会一次性检查六项：服务进程、Node 监听地址、Nginx 与证书、
本机功能自测（含口令门禁）、证书续期任务、公网连通性。

**期望输出**：

```
✓ 8000 只监听 127.0.0.1 —— 已收回本机，公网打不通 ✓
✓ 443 在监听 ✓
✓ 证书签发对象是 IP：IP Address:1.2.3.4
✓ HTTPS 首页返回 200 ✓
✓ WebSocket 升级正常，且口令门禁生效（bad_key）✓
✓ 公网 HTTPS 通（200）✓
✓ 8000 公网已关闭（连不上）✓ —— 这正是想要的结果
```

核心要点：

```bash
# 服务器上
npm install --omit=dev
ALT_PORT=0 PORT=8000 node server.js
```

Nginx 配置**必须**包含 WebSocket 升级头，否则页面能开但消息发不出去：

```nginx
location /ws {
    proxy_pass http://127.0.0.1:8000;
    proxy_http_version 1.1;
    proxy_set_header Upgrade    $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_set_header Host              $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_read_timeout 3600s;      # 长连接别被提前掐断
}
```

> ⚠️ **HTTPS 是必须的**：网页走 HTTPS 时浏览器会**禁止** `ws://` 明文连接，
> 聊天必须用 `wss://`，所以 TLS 终结层不可省略。
> 客户端代码会自动判断协议，无需改代码。

**部署时改这些环境变量**：

| 变量 | 默认 | 说明 |
|---|---|---|
| `PORT` | `8000` | 主端口，云平台会注入 |
| `HOST` | `0.0.0.0` | 容器/云主机必须保持 `0.0.0.0` |
| `ALT_PORT` | `3000` | 部署时设 `0` 关闭（平台通常只开放一个端口） |
| `DATA_DIR` | `./data` | 容器里应指向持久化卷 |

### 怎么确认朋友真的进来了

聊天室左下角有**在线成员列表**，朋友上线后会出现在里面（显示不同的昵称和头像色）。
你也可以直接发条消息，看他屏幕左边是否实时出现。

如果他打不开，按这个顺序排查：

| 现象 | 原因 | 处理 |
|---|---|---|
| 一直转圈 | 防火墙 / 安全组拦截 | 放行端口；云主机还要检查安全组 |
| 页面打开了但发不出消息 | Nginx 缺 WebSocket 升级头 | 见方式 C 的 Nginx 配置 |
| 浏览器报"混合内容" | 页面 https 但 WS 是 ws:// | 配好 TLS；代码本身会自动切 wss |
| 他打开的是自己的 localhost | 用了 `localhost` 地址 | 必须换成公网地址（方式 A/B/C 任一） |
| 提示"房间口令不正确" | 他用的链接里没带 `#key=xxx` | 把启动器打印的**完整链接**（带 `#key=`）发给他 |

## 二·五、房间口令（内测期间的门禁）

内测阶段房间是**私有的**：除了你和你朋友，别人进不来。

- 服务端启动时自动生成一个 12 位口令，写进 `data/room.key`；
- 启动器会把口令直接拼在分享链接里：`https://xxx.trycloudflare.com/chat#key=xxxxxxxxxxxx`
- 朋友打开这条链接就能直接进来，不用手输；
- **没有口令（或口令不对）的连接会被当场拒绝** —— 不占昵称、不出现在成员列表里、历史消息里也不会有他；
- 你自己从本机打开 `http://localhost:8000/chat` 不用带口令：页面会自动向服务端要（这个接口只对本机直连开放，走公网隧道过来的一律 403）。

> 口令是**唯一数据源**在 `data/room.key`，服务端写、其它人只读。
> 想换口令，删掉这个文件重启即可。
> 想要「谁都能进」的公开房间：设环境变量 `ROOM_KEY=''` 启动。


### 昵称唯一性是怎么保证的

消息表只存 `sender_id`，昵称是读取历史时实时关联 `users` 表查出来的。
所以只要某人发过言（消息还在保留期内），他的昵称就会一直出现在历史里 ——
这时候让别人用同一个昵称，历史中就会同时出现两个「小满」，谁是谁根本分不清。

因此**昵称占用权的载体是 `users` 表的那一行**，而不是内存里的在线名单：

| 状态 | users 行 | 昵称是否被占用 |
|---|---|---|
| 在线 | 在 | ✅ 占用 |
| 离线、但发过言（消息还在保留期） | 在 | ✅ 占用（历史去重的关键） |
| 消息全部过期 | 被清理掉 | ❌ 自动释放，可被重新使用 |

具体做法：

- `users.name` 上建 **唯一索引** `idx_users_name`，从存储层兜底，任何写入路径撞名都会直接失败；
- 新用户上线写入时若撞名（两人同时上线抢同一个名字），自动换后缀重试；
- 老版本遗留的重名数据在启动时由 `migrateUniqueNames()` 拆分：消息最多的人保留原名，其余依次加数字后缀；
- 自动分配昵称的昵称池扩到 **60 个**，池子用完后改为「小满2」「小满3」往下排，而不是另换一批随机名（避免二次撞车）；
- 在线成员每 30 秒刷新一次 `last_seen`，避免「一直在线但久不发言」的人被清理任务当成僵尸行删掉、连带丢掉昵称占用权。

## 五、常见问题

**Q：页面能打开，但一直显示「连接中…」**
检查浏览器控制台 Network 面板里 `ws://` 或 `wss://` 的连接状态。若页面是 HTTPS 而 WS 是 `ws://`，会被浏览器直接拦截——这正是必须配 Nginx TLS 的原因。

**Q：刷新后消息还在吗？**
在。只要还在 7 天保留期内，消息保存在 SQLite 里，重启服务也不丢。

**Q：能撤回别人的消息吗？**
不能。撤回只对本人 2 分钟内发出的消息生效，权限校验在服务端完成。

**Q：改了昵称，之前的消息会变吗？**
会。消息表只存用户 id，昵称在读取时实时关联，所以历史消息里的名字会一起更新——包括已经显示在别人屏幕上的消息（他们会收到广播后同步刷新）。

**Q：刷新页面后我的消息跑到左边去了？**
这是**旧版本**的问题，已修复。原因：服务器每次连接都发一个全新的身份 UUID，
刷新后你的历史消息的 `sender_id` 对不上新身份，就被当成"别人发的"渲染到了左边。

现在浏览器会在 localStorage 里存一个 `client_id`，**刷新 / 关掉重开仍是同一个人**
（id、昵称、头像色都不变），你的历史消息依然在右边。

**Q：朋友怎么进来？**
给他一个**公网地址**，不是 `localhost`。三种方式见上面「让朋友进来」章节：
本机穿透（Cloudflare Tunnel，最快）、家庭宽带直连、或云服务器 + 域名。

**Q：为什么 localhost 朋友打不开？**
`localhost` 永远指向"访问者自己的那台电脑"。你朋友敲 `http://localhost:8000`，
连的是他自己的电脑（他的 8000 端口上什么都没有），不是你这台。
必须换成公网地址。

**Q：朋友打开后是我的号吗？**
不是。每个浏览器有自己独立的身份——靠 localStorage 里的 `client_id` 区分，
所以你和朋友是两个不同的人，昵称、头像色都不同，在线成员列表里各占一行。
同一个人刷新页面则保持原身份不变。

**Q：为什么改昵称会影响历史消息？**
这是需求里明确要求的「改昵称后显示改后的」。副作用是昵称必须落库（`users` 表），否则服务端无法解析历史消息该显示谁的名字。这张表不作为功能暴露，仅用于解析显示。

**Q：打开 http://localhost:8000 是入口页，聊天室在哪？**
入口页是「聊天网页」四个字的行楷大标题，点页面任意处立即进入，或者等 5 秒倒计时自动进入。
聊天室本体在 <http://localhost:8000/chat>，也可以直接收藏这个地址跳过入口页。

**Q：头像只有 6 种颜色，人多了会撞色吗？**
不会。用户指定的 6 个「基础款」（浅绿 / 浅粉 / 浅黄 / 浅紫 / 白色 / 黑色）被展开成
**6 色系 × 4 色阶 = 24 色**，并且**每个色系内部的任意两色，亮度差（YIQ）都 ≥ 20**，
所以浅绿和深浅不同的浅绿一眼能分开。实测 **20 人同时在线，24 个头像底色两两不同**。

分配策略是"**优先挑当前用得最少的色**"（不是"只在没被用过的色里挑"）——
后者一旦某种颜色被占满就开始随机重复，会出现 4 个人共用一个浅紫的情况。

另外头像**不只看颜色**：消息区显示的是「昵称两字缩写 + 底色」，
所以"小满"和"小雨"即使首字相同，靠底色深浅和第二字也能分开。

**Q：白色头像在浅蓝背景上看不清？**
白色头像统一加了 `inset 0 0 0 1px rgba(0,0,0,.12)` 描边，浅色底上的头像文字会自动切成深色，
黑色底则切白色，浅蓝背景上都能看清。

**Q：朋友打开后是我的号吗？**
不是。每个浏览器有独立的身份（localStorage 里的 `client_id`），你和朋友是两个不同的人，
昵称、头像色都不同，在线成员列表里各占一行。**同一浏览器**刷新页面则保持原身份不变。
